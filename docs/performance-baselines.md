### 查询计划与正确性门禁

SQLite 的实际 `EXPLAIN QUERY PLAN` 关键行如下：

```text
SCAN library_entries USING COVERING INDEX ix_library_entries_created_work
SCAN work_search VIRTUAL TABLE INDEX 0:M4
SEARCH works USING INDEX ix_works_status_doi (status=? AND doi>? AND doi<?)
SEARCH document_versions USING INDEX ix_document_versions_work_representative (work_id=?)
```

固定 20,000 篇 CI 样本另外证明：

- 无查询列表执行数据库 `COUNT + ORDER BY + LIMIT/OFFSET`，不会先 materialize 全库。
- 中文标题和英文作者由安全编译的 FTS5 候选完成；DOI 使用规范化精确/前缀范围。用户文本不会直接拼入 SQL 或作为原始 FTS 操作符执行。
- 返回一页时，Work、LibraryState 和 DocumentVersion 总查询数有固定上界，不随页面条目数增长；代表版本仍按“合法可访问、最近更新、最完整、最近入库、稳定 ID”选择。
- 论文库迁移只追加 `0031_library_query_indexes`，可降回 `0030_user_preferences`，不会重写已发布迁移或删除业务表。

- 与第 1 节使用同一开发机；Python 3.12.12，当前迁移头 `0032_identity_candidate_indexes`。

20 次候选数量均为 `256`，20 次匹配均为 `auto_similarity`。这组构造数据故意让常见词产生超过上限的 FTS 命中，以验证最坏候选压力下硬上限仍关闭；它不是对真实语料候选数量分布的估计。

RED 门禁在同一固定 20,000 Work 小样上证明旧实现实际调用 20,000 次 `paper_similarity`；新实现只读取 FTS 返回 ID 对应的 active Work。标点/大小写、中文—英文空格、作者顺序、轻微改写、不同 DOI 和完全不同题目另有金样，保持原有自动合并/人工审阅阈值。

SQLite 实际查询计划：

```text
SCAN work_search VIRTUAL TABLE INDEX 0:M4
USE TEMP B-TREE FOR ORDER BY
SEARCH works USING COVERING INDEX ix_works_status_normalized_title (status=? AND normalized_title>? AND normalized_title<?)
SEARCH works USING COVERING INDEX ix_works_status_published_at (status=? AND published_at>? AND published_at<?)
```

正常路径先查 DOI，再由安全转义且支持词形前缀的 FTS 标题 token 与作者词项给出 BM25 排序候选；FTS 的临时排序只处理其倒排匹配结果，最终相似度公式不变。FTS 缺失或查询不可用时，先做精确题名探测，再执行带 `LIMIT` 且索引顺序可提前停止的标题前缀与可选发表年份查询；两条降级计划均使用 covering index，且没有临时排序。退化会在 `CandidateSearchDiagnostics` 和人工审阅证据中标记 `degraded=true`；绝不回退 Python 或 SQL 全库排序。`0032_identity_candidate_indexes` 只追加两个含稳定 ID 尾列的 Work 复合索引，可独立降回 `0031`。
